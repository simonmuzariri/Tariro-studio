# REA Runtime Analysis — PictoBlox 9.0.0

## Startup sequence (VERIFIED from runtime log and REA page inspection)
1. Custom `electron-updater-linux` module; checks `resources/package-type` (`deb`) for the beta-autoupdate path.
2. Module imports take ~2.3–2.8 s (`IMPORTS:` log line); the splash window appears at ~3.4–5.6 s.
3. Port allocation: `pictoBloxPort 21679`, `pictoBloxSocketServerPort 21677` (default = assigned). Then "Socket server is listening at 21677".
4. OS info probe (kernel string, `x64`), free-memory polling every few seconds (`NNNN Free Memory` lines).
5. Renderer loads `http://localhost:21679/` → 9 scripts (~165 MB of JS in total). The full GUI mounts behind the launcher modal.
6. Python runtime discovery: `ppyPath …/python/linux/ppy-{basic,advance,ml}/ppy` (copied into the user-data dir on first run). `GET_TF_BACKEND_STATE true`.
7. Update check against provider `github` / `LLK/scratch-gui` (from `app-update.yml`): "Update for version 9.0.0 is not available".
8. `ipcMain | storeCacheModals COMPLETED`.

## Workspace initialisation (VERIFIED)
- On choosing **Blocks**: the default sprite plus backdrop project loads, the Motion category is selected, Stage mode is the default, and the board is none.
- On choosing **Junior Blocks**: a tutorial modal plus a horizontal block palette.
- **File → New** asks to save and then returns to the launcher (environment re-selection).

## Code generation (VERIFIED behaviour, implementation UNKNOWN)
- Generation is **live**: C++ re-renders after every block drop with no explicit "generate" action.
- Only stacks under the board hat (`when <Board> starts up`) are emitted. The green-flag stack (grey in Upload mode) is ignored.
- Template:
  ```
  //This c++ code is generated by PictoBlox
  [#includes]                       (U: not yet seen)
  //MACROS are defined here          (only when needed)
  <globals>
  void setup() { <pinMode…hoisted> <statements before forever> }
  void loop()  { <forever body> }
  ```
- Value coercion: HIGH→`true`, seconds→`delay(n * 1000)`.

## Program execution
- **Stage mode** (VERIFIED): Scratch-VM threads; green flag starts hat scripts; stop halts them; the running stack glows; sprite state is visible in the property fields.
- **Upload mode** (INFERRED): renderer sends `uploadCode` (C++ text plus board) → main writes the sketch (`Documents/Pictoblox/cpp_scripts/arduino.ino`, I) → `arduino-builder -compile -logger=machine …` → parses `===info ||| Progress {0}` / `Sketch uses {0}` → `buildComplete` → `avrdude`/`esptool` → `uploadStart`/`uploadComplete`/`uploadError` events → Log pane.
- **Hardware live mode** (INFERRED): Stage mode with a board connected needs PictoBlox firmware (Upload Firmware button; `firmwareFiles` per board; `GET_FIRMWARE_TYPE`, `EMIT_FIRMWARE_VERSION`). Blocks send commands over serial/BLE (`sendDataToHardware`, `sensorRead`, `serialRead`). Protocol is **U**.

## Console / errors
- Upload mode has **Log** and **Serial Monitor** tabs (V). Error alerts are routed through `sendAlert` (I), e.g. `eraseFlashFailed`.
- Renderer console was not captured in this pass (U).

## Shutdown
- `window-all-closed`, `closePictoBlox` and `RESTART_APP_LATER_AFTER_UPDATE` handlers exist (I). Not exercised (U).

## Observable vs assumed
Everything marked V was seen on screen or in REA Evidence. Main-process internals marked I come from static text of the shipped bundle, not from observed execution.
